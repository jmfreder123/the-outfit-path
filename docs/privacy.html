Adults only

The Outfit Path is intended only for people age 18 and over. Before any wardrobe, account, or cloud scripts load, the app asks the visitor to confirm that they are at least 18. It does not ask for a birth date or identity document. The confirmation is a self-attestation, not verified proof of age, and is stored only as a value in that browser tab's session storage. It is not included in the cloud backup.

If a visitor selects “I am under 18,” the wardrobe, account, and cloud scripts do not load and no age response is saved. The hosting provider still receives ordinary request data needed to deliver the initial page. A visitor can bypass a browser-only gate, so this control cannot guarantee age or eliminate legal risk.

Invite-only beta

There is no public account signup in the app. John M. Fredericks chooses whom to invite and uses Supabase's administrative invitation flow. Prospective testers should be invited only after they state that they are age 18 or older. That operator check and the in-app gate are self-attestations, not verified age assurance. Supabase's live “Allow new users to sign up” setting was disabled by John M. Fredericks and verified off after reload on October 24, 2026; anonymous sign-ins were off and email confirmation was on.

After the 18+ gate, signed-out visitors must sign in before wardrobe access. A valid invitation or recovery callback requires password setup before continuing. Password-reset requests return a generic response that does not confirm whether an account exists. An account that optionally enrolls an authenticator app must also complete its second factor. Signed-out, expired, or second-factor-pending sessions see an account gate; the separate guest copy remains stored locally but hidden.

Supabase receives the invited email address and sends the invitation email. The invitation link should not be shared. The app never contains an administrator or service-role credential. Invite administration, public-signup configuration, and user management remain in the protected Supabase dashboard.

How data is used

  • Provide the closet, outfit suggestions, saved looks, local preference learning, backup, and authentication features.
  • Protect accounts and isolate each signed-in user's cloud document through database access policies.
  • Diagnose failures and maintain the service where provider logs are available.

The preview contains no app analytics, advertising trackers, or behavioral advertising. It does not use a hosted AI inference API. The optional recognition model runs in the browser.

Service providers and external requests

  • Supabase: invitation email, authentication, and the optional wardrobe JSON backup.
  • GitHub Pages or the eventual hosting provider: site delivery and ordinary request logs.
  • jsDelivr: pinned browser libraries and optional recognition runtime files.
  • Hugging Face and its delivery infrastructure: the optional recognition model, pinned to a specific revision.

The user's image pixels are processed in the browser and are not intentionally uploaded to those recognition-resource providers. Download requests still disclose ordinary network metadata. Provider retention and international-transfer terms have not been verified for this draft; review their current policies before launch.

Storage, retention, and deletion

  • Local wardrobe data remains until the user resets the app, clears site data, or the browser evicts it.
  • Signing out removes this app's session from the current browser but does not delete the Supabase account or cloud row.
  • A manual cloud upload overwrites that user's previous cloud document. The current preview has no self-service cloud-copy or account deletion control.
  • Signing into a different account switches the visible local wardrobe to that account's separate browser namespace. A preserved guest wardrobe is not assigned or uploaded automatically; copying it into an account requires a separate confirmation and leaves the guest copy intact.
  • Exported backup files remain wherever the user stores or shares them and are not encrypted by the app.

Security

The app uses HTTPS service endpoints, a publishable browser key, row-level database policies, input validation, output escaping, a restrictive content policy, and pinned dependencies. The privileged service key and database password are not used in frontend code. No system can be guaranteed secure; the security review still requires live two-account isolation testing and an approved deletion process before launch.

User choices and requests

Users can export a full local backup, reset local data, pause local preference learning, and sign out of the current browser. Rights such as access, correction, deletion, restriction, objection, or portability depend on the user's jurisdiction. Requests can be sent to jfredericks4@gmail.com. This contact route still needs an approved identity-verification and request-handling process before launch.
